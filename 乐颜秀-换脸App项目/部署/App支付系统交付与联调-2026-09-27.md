# App 支付系统交付与联调

更新时间：2026-09-27。范围：乐颜秀 Android App。源码为 `源码/app` 的当前工作区，不能用 Git HEAD、旧部署包代替。小程序支付由独立分线负责；共享源码中的现有小程序改动予以保留。

## 当前结论

本地支付开发、接口测试、数据库并发与恢复验证、界面验收已经完成。尚未部署，未修改正式环境变量，未发送真实短信、未执行真实扣款或退款，未发布套餐价格，未重新交付 APK。正式收款仍为 NO-GO。

采用现有业务代码 + 开源协议组件 + PostgreSQL 交易账本。没有迁移整套聚合支付平台。微信 API v3 的 RSA 签名、签名字符串和 AES-GCM 解密复用 `wechatpay-axios-plugin@0.9.6`；HTTP 出站限制、原始响应验签、金额及商户校验仍由本项目适配层负责。短信使用阿里云官方 SDK `@alicloud/dysmsapi20170525@4.6.0`，未内置生产测试码。

## 已实现的业务闭环

- 次数包：次数不设置到期日，按订单独立保存余额。
- 30 天套餐：不自动续费；每期独立次数与有效期，提前续购顺延，未用次数不结转。没有开放无限云端算力、永久云端免费使用的商品类型。
- 套餐由后台 owner 发布；订单保存商品名称、金额、次数、类型、有效期规则及已确认条款版本。客户端不能指定成交金额。
- 下单幂等、商户/App/订单/币种/金额核对、到账通知幂等；主动查单补偿漏通知。关停新销售不等于关停历史订单查单和退款。
- 生成任务先冻结次数，成功核销、失败释放。按最早到期批次扣次；在有效期内受理、到期后失败的任务返还 7 天有效的补偿次数。
- 退款按原订单计算：次数包按剩余次数比例；30 天套餐在付款后 7 天内且未使用可申请全额退款，其余取未用次数比例与剩余时间比例中的较小值，向下取整到分。制作中的任务须先完成。申请后冻结该单全部剩余额度；成功退款后终止这些权益。未来续购期不会因另一订单退款自动提前。
- 用户先查看可退金额再确认；提交时金额若变化则拒绝，并要求重新查看。渠道结果不明时保持冻结；后台不能把已提交渠道的退款随意当作失败释放。
- 手机号绑定、验证码找回原账号、后续设备登录映射回原账号。手机号只保存 HMAC 摘要和脱敏展示；验证码保存带独立密钥的摘要，5 分钟有效、最多 5 次尝试；手机号、设备、IP 限流及每日全局短信预算同时生效。不会自动合并两个已有订单/绑定的账户。
- 后台维护次数包和 30 天套餐、查询订单、审核部分退款、查询退款结果、展示实际退款金额、下载并核对渠道日账单。
- 日账单使用已验签的下载清单，固定微信域名，校验文件 SHA1，保存 SHA256 和差异报告。不通过账单文件自动改余额。未识别的账单格式、无账单/生成中、下载失败均不视为核对成功。

## 部署顺序与禁止误操作

1. 保持 `PAYMENT_MODE=closed_test`，先准备独立的 PostgreSQL 数据库、最小权限服务账号、TLS 与正式备份策略。正式环境连接要求证书校验；不能在连接串里关闭 SSL 验证。
2. 备份旧合规/账户/订单数据，核对是否存在真实或闭测订单。`BILLING_BACKEND=legacy` 为默认值，旧数据未自动搬迁。
3. 先执行 `node server/scripts/app-billing-migrate.mjs` 看迁移说明；只有审查目标库后才使用 `--apply` 创建新增表。脚本不导入、不覆盖旧账本。
4. 配置 `BILLING_BACKEND=postgres` 与 `BILLING_DATABASE_URL`。若旧账本含任何订单，启动会报 `LEGACY_ORDERS_REQUIRE_REVIEWED_MIGRATION`，不可通过清空原文件绕过。需要另做经核对的历史订单/权益迁移后再切换；当前没有自动迁移历史支付数据。新账本在商户/App 配置齐全时绑定该组合，之后配置不匹配会拒绝启动，防止误接其他商户账本。
5. 账户/会话/同意记录仍使用原合规存储，因此仍受其单实例/持久卷及恢复验收条件约束。独立交易账本支持并发不代表整个 App 已支持跨节点多实例。
6. 通过秘密管理配置微信商户/App 绑定、商户私钥、API v3 密钥、平台公钥、两个公网 HTTPS 回调地址；配置阿里云短信签名/模板和独立短信凭据。勿把值写入文档、日志、Git 或聊天。
7. `ACCOUNT_OTP_SECRET` 为稳定、独立的随机密钥，至少 32 字符，必须受控备份。直接更换会改变手机号摘要，不能无计划轮换；密钥轮换需专门迁移方案。短信模板变量为 `code`，预算默认每天 200 次。
8. 在目标库完成并发、重启、备份恢复、权限和迁移核验，写入真实验收报告并配置 SHA256；报告模板见下文，不要把示例的 false 改 true 当成测试。
9. 只为指定测试账号开启 `merchant_test`，通过安卓真机执行真实小额支付、取消、断网返回、重复通知、漏通知查单、全额/部分退款、手机号换机找回及次日日账单。这个模式也会真实扣款，须先确定账号和扣款预算。
10. 核定供应商单位成本、套餐适用功能、价格、退款条款及客服流程；通过后台 owner 发布正式 SKU。预览中的 9.90/49.90 均为示例，未发布。
11. 完成 App 原有实名、内容安全、资质、隐私和素材授权门禁后，重新构建/签名/真机验收发布包；最后才允许开启 `live`。本次工作没有把其他合规阻断项移除。

`PAYMENT_RECONCILE_ENABLED=true` 开启待确认支付/退款查单；`PAYMENT_BILL_RECONCILE_ENABLED=true` 开启北京时间 10 点以后、每小时尝试一次的昨日账单核对，成功后当天不重复自动核对。缺失日期可在后台手工选择日期补查。账单接口仅支持微信允许的历史范围；应另行配置调度存活和差异告警。

首次切换前如需回滚，保持关闭收费并恢复原配置即可。新库开始接收真实订单后，不得直接切回旧账本继续卖；应暂停新销售，保留查单/退款处理，核对两边账务后决定迁移。未确定结果的生成任务也不能仅按超时批量释放，应先核实供应商状态。

## 验收报告格式

`BILLING_ACCEPTANCE_EVIDENCE` 指向 JSON 文件，`BILLING_ACCEPTANCE_SHA256` 固定其文件摘要。以下是未验收模板：

```json
{
  "kind": "app-postgres",
  "result": "pending",
  "testedAt": "",
  "reviewedBy": "",
  "checks": {
    "parallelConnections": false,
    "restartPersistence": false,
    "backupRestore": false,
    "leastPrivilege": false,
    "legacyCutoverReviewed": false
  }
}
```

`PAYMENT_ACCEPTANCE_EVIDENCE` 与 `PAYMENT_ACCEPTANCE_SHA256` 对应正式商户验收报告：

```json
{
  "kind": "wechat-app",
  "merchantId": "填写已验收商户号",
  "result": "pending",
  "testedAt": "",
  "reviewedBy": "",
  "checks": {
    "realPayment": false,
    "duplicateNotify": false,
    "refund": false,
    "lostCallback": false,
    "dailyBill": false,
    "nativeReturn": false,
    "phoneRecovery": false
  }
}
```

只有实际通过、审查人/时间/商户匹配且哈希一致的报告才通过门禁；报告仍是运维签认记录，不能代替留存实际订单、渠道回执、日志和测试证据。生产还要求 `ACCOUNT_RECOVERY_VERIFIED=true`、真实短信配置以及两个对账任务开启。

## 核心文件

- `server/payments/database.js`、`ledger.js`：独立交易表、行锁、权益批次、部分退款与账务核对。
- `server/payments/accounts.js`、`account-routes.js`、`sms.js`：手机号验证和恢复。
- `server/payments/wechat.js`、`routes.js`、`reconciliation.js`：微信接口、金额核对、售后和日账单。
- `server/payments/runtime.js`、`config.js`、`evidence.js`：切换边界与验收门禁。
- `src/views/Purchase.tsx`、`src/components/PaymentIdentity.tsx`、`src/admin/BillingPanel.tsx`：购买、恢复、退款和后台管理。
- `scripts/payment-preview.mjs`：仅本机模拟页面验收入口，不在正式产品入口加载，不作为真实商户证据。
