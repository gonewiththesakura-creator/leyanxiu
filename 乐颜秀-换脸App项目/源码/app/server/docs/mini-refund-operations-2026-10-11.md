# 小程序最小退款运营入口（本地候选）

本次复用现有微信登录、持久会话和唯一虚拟支付账本。没有新增通用管理后台、第二套退款计算、运营密码或客户端密钥。这里只实现审核现有退款申请；渠道退款仍由既有 outbox 和对账执行，审核通过不能被显示为已经到账。

## 服务端权限和接口

正式入口读取 `XPAY_REFUND_OPERATOR_USER_IDS`，默认空。只能配置在同一 AppID/env0 数据库已经存在的 canonical `usr_...` 账号；配置不会授予旧后台的其他写权限。当前未配置真人运营账号，本地测试只使用合成身份。

`mini-refund-operator.js` 在同一个 `miniIdentity`、同一个 ledger/database 上挂载：

- `GET /api/mini/operations/status`：有效微信会话返回唯一业务字段 `{operator:boolean}`，无运营列表、用户ID、电话、密钥，且不缓存。
- `GET /api/mini/operations/refunds`：最近最多100条退款投影。
- `GET /api/mini/operations/refunds/:id`：原退款投影。
- `POST /api/mini/operations/refunds/:id/review`：只接受 `confirm:true`、布尔 `approve`、展示时的 `expectedOrderId` 和整数分 `expectedAmountFen`。

读列表、读详情、审核均要求服务端运营白名单和最近5分钟内的有效微信登录。审核又在原账本事务内部检查会话未撤销、同 AppID/env0、原订单与金额未变化；复用同用户锁、原状态转移、冻结权益、审计和 outbox。拒绝申请通过原账本恢复相应冻结权益；通过只入退款队列。旧 admin 路径保持拒绝，正式服务不挂载沙箱自助退款确认。

## 原生页面和中断恢复

`pages/service/index` 只在服务端精确返回 `operator:true` 时显示退款审核入口。页面隐藏、身份切换或发现接口失败都会隐藏入口。界面按钮不是授权依据，手工深链或伪造本地标志仍由服务端拒绝。

`pages/refund-ops/index` 使用 `refund-operations.js` 和既有支付客户端的微信登录/云托管传输。运营员先重新登录、查看列表和详情，确认服务器展示的订单与人民币金额，再选择通过或拒绝。客户端在提交前再次登录同一账号并读回原金额；离开页面、金额变化、账号变化、存储失败或已有未知提交都会阻止 POST。

提交意图在 POST 之前按运营账号持久保存，只存退款编号、订单编号、分金额和决定。响应丢失时页面立即显示锁定，重新进入和刷新只 GET 原退款；原记录仍为 requested 时保持锁定，不自动重发。原记录变为可确认的后续状态才清除此本地锁。若长期未确认，需要运营人员核对原记录，不能通过新建退款或清理本地记录绕过未知状态。公共支付客户端已有的“明确401拒绝后重新认证”合同保留；网络超时或503不会重放审核。

正式购买页现在同样展示本人退款记录和金额，包括待审核、处理中、完成、拒绝和异常。只有 `ledgerOnlySandbox` 为真时才展示和调用沙箱自确认。`processing` 明示尚未确认到账；`abnormal` 明示权益保持冻结，不能宣称已经退回。

## 本地验证与边界

本轮专项：运营后端10项、原生运营客户端/页面13项、服务帮助客户端26项、支付客户端57项（含18子用例），共106项通过。独立代理对前105项复跑通过并额外审查关键中断场景；随后新增的真实客户端→Hono→持久SQL→账本提交响应丢失集成在运营10项中通过，恢复后仍仅一次审核POST、一次审计转移和一个退款outbox。

使用本地隔离 SQLite 的明确 MySQL 形状端口测试业务/HTTP/持久身份，不能代替 MySQL 锁行为或云端验收。没有调用真实退款、购买、微信登录供应商或其他付费服务，没有配置真实运营身份或发布小程序。还需后续以服务端指定真人运营账号进行真机入口/退出/重新登录验收，部署既有对账任务后核对渠道终态和用户实际到账。正式开售门禁仍由聚合 readiness 决定，本页面本身不会开启销售。
