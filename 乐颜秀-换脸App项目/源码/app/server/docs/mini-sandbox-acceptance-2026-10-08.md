# 微信虚拟支付沙箱验收清单（2026-10-08）

本清单只覆盖现有小程序 `buildtest` 的虚拟支付沙箱。目标是证明“同一用户下单一次，渠道确认支付后只增加一次权益；退款确认后撤回对应权益”。图片生成交付、正式收费、iOS 支付、提审发布分别验收，不能由沙箱通过推导完成。

本清单最初由只读审计形成。主执行随后于 2026-10-08 在既有 Chrome 现场核对 AppID、OfferID 与开发版 `photo10 / 990 分 / 10 次`，备注为“开发联调样例暂不发布”，状态未发布，现网商品为空；这不是正式售价批准。代码和云端的后续进展见执行记录，不以本清单代替真实渠道终态。

## 资金语义修正与本轮实际结果（2026-10-08）

撤回此前“沙箱不会产生真实扣款”等保证。`env=1` 和沙箱 AppKey 是渠道环境参数，已核对官方合同未支持“因此一定不扣真实资金”的推论。沙箱联调可能实际扣款，以微信收银台和支付记录为准；图片创作尚未开放。不得为绕过问题切到 `env=0`，下一次拉起支付前必须由用户明确确认该笔具体金额，不能把一般性的“继续测试”当作金额确认。

agent 在 Android 真机明确执行一次 `requestVirtualPayment`，用户报告微信收银台提示余额不足。查原单最初返回 `XPAY_HTTP_UNCONFIRMED`。随后核对发现微信接口云调用已开启，但接口路径白名单为空；补充准确路径 `/cgi-bin/stable_token` 和 `/xpay/query_order` 后，继续查询同一原单，微信返回订单状态 `6`，本地记录变为 `closed`。该单标价 `990` 分，权益为 `0`，没有退款记录。最终账本又出现一笔17:29:19创建的990分android订单，触发来源未确认；逐单复核最终共2笔closed、权益桶及退款均0。标价不是实际收款金额；本轮没有成功支付或退款验收。

后续 `buildtest-011` 已完成部署，100%流量；唯一配置变化为XPAY_MODE=closed，保留查单/对账。真实私有调用验证新购503/XPAY_NOT_READY，负测前后均2笔订单；公网两条入口仍403。最终运行时为devtools，资金提示修正已在模拟器截图检查，不能冒充安卓手机UI验收。发布号、清单、任务及完整证据见执行总记录。

| 数据库、备份、图片可交付 | 上述支付文档没有要求另购数据库，也没有本项目 `reviewed`、13 表等配置。 | 这些是实现和运营保障。继续复用已选数据库；`reviewed` 不能用来伪造图片真实可用性。 |

## 审计起点发现的本地缺口

1. `mini-sandbox-service.js` 的开放条件目前仅为 `XPAY_MODE=sandbox` 加非空目录，且目录的权益种类能匹配内部 `reviewed` 用途；`testUserIds=[]`，通用路由只对 `merchant_test` 检查白名单。沙箱若要限制到测试者，需要显式实现并测试。
2. 当前独立服务明确 `generationAvailable=false`。支付账本联调可以验证测试权益，但应有独立、清楚的沙箱语义，不要借 `reviewed=true` 对外暗示已经能制作图片。对外正式销售必须等图片交付链路接通；沙箱测试可能实际扣款，仍需按具体金额确认。
3. `mini-sandbox-server.js` 仅在 `XPAY_RECONCILE_ENABLED=true` 时每 30 秒执行补查/发货；当前部署记录为 false。云回调刻意保留发货 outbox，因为普通调用者的 HTTP ACK 不代表微信收到了发货确认。开沙箱前应启用并验证这一条补偿路径；实例缩容/重启后还应证明积压任务能恢复。
4. 当前独立服务所有管理员路由固定 403。用户退款申请只能到 `requested`；要测试主动退款，需要受限、可审计的沙箱运维途径将指定申请审核为 `processing`，然后由同一持久化 outbox 发起。不得新增公开“退款调试”接口，也不得在 SQL 中伪造渠道退款成功。
5. 官方当前退款 API 将 `refund_reason`、`req_from` 定义为字符串，本地 `wechat.js` 仍发数字 `2`、`1`。实现者应按文档修正并做序列化合同测试。此项是本轮发现，未在本文件任务中改代码。[退款 API][refund]
6. 当前自动部署脚本有上次操作的成功记录和一次性升级约束。修改沙箱环境配置前应准备可审查的受控升级，不删除 pending 记录或绕过远端状态校验来重跑旧部署。

上述为审计开始时发现的缺口。2026-10-08 本地已补齐 1、2、4、5、6，并为 3 准备强制开启的沙箱配置；本人退款确认使用现有 Bearer、白名单和严格 env1/归属校验。合并后相关业务测试 148/148、部署测试 40/40 通过，包含图片任务26项；使用隔离数据库和渠道替身，不等同真实渠道支付/退款验收。

资金提示及状态弹窗后续修正：`tests/virtual-payment-client.test.mjs` 本地 32/32 通过，覆盖具体金额确认取消不调用购买、确认期防双击、待确认键保留，以及刷新后的同一订单优先于旧购买响应。`pending → paid`、`paid → refunded`、`paid → refund_pending`、`closed` 和未找到同单分别显示对应状态；关闭只说明渠道确认订单关闭，不推断钱包一定未扣款。客户端修正未在这项文档任务中编译到真机，不能记为真机 UI 验收。

## 经审查的最小沙箱设计（实施前的合同）

独立服务保留硬性 `env=1`，将购买 readiness 改为“purchaseEnabled + 有效非空测试目录 + 非空服务端测试用户白名单”。不再用生产图片用途的 `reviewed` 标志放行纯账本测试；完整生产 runtime 的可交付门槛保持独立。health/products 明确 `ledgerOnlySandbox=true`、`generationAvailable=false`，客户端显示“沙箱联调可能实际扣款，以微信收银台为准；图片创作尚未开放”，支付前另行显示具体金额并要求确认，取消不发起购买且不清除待确认订单。非白名单用户不得创建订单；products 的可购买显示也应反映当前用户权限。白名单值不得通过公开接口或日志泄漏。

无需新管理员登录的退款路径可以是仅独立服务注册的 `POST /api/mini/payments/sandbox/refunds/:id/confirm`：

1. 通过现有 Bearer 获取真实服务端 userId，并检查服务端白名单；配置/数据库绑定/目标订单都必须为同 AppID、env=1。
2. 只读取本人既有退款申请；订单、金额、退款编号、申请人、状态全部以账本为准。客户端只提交明确 `confirm:true`，不能指定其他用户、金额或审核身份。
3. 以明确的沙箱本人确认策略执行 `ledger.reviewRefund`，记录可区分的 reviewer 和服务端来源元数据，复用既有事务、冻结权益、outbox 和退款查询。不存在申请、他人申请、错环境、拒绝过或状态未知均拒绝；已处理中/已完成的同一确认只返回现状，不再次提交退款。
4. 官方 `req_from='2'` 表示用户自行发起；此途径应选它，不能继续标作人工客服来源 `'1'`。原因按实际声明选官方字符串枚举，例如用户主动退款为 `'3'`。来源/原因值由服务端策略产生。
5. 销售恢复 closed 后，仍允许白名单用户处理原沙箱订单的退款收尾。普通用户和生产服务不能使用此确认接口；通用管理员接口仍为 403。

这是一项只用于沙箱的显式自助审核策略，不代表正式退款审核、客服后台或 iOS 退款已完成。确认页必须显示具体申请金额；原路退款结果以渠道确认为准，不能保证退款“不涉及真实资金”，也不能把请求受理当作到账。

## 最小执行顺序

1. 只读核对：MP 的 AppID、OfferID、开发版 photo10 及分价；数据库仍是目标私网沙箱、应用账号仅该库 CRUD；云服务当前版本、closed 状态、公网拒绝和消息路径仍正确。
2. 本地补齐：测试访问控制、清楚的沙箱标识、补查/发货运行条件、受限退款审核途径及官方参数类型。保持真实图片入口关闭；生成的新版本先运行隔离测试与审核。
3. 受控部署：固定 env=1，仅一份已核对测试商品，使用沙箱 AppKey；服务 API 只按受控方案对测试者开放。部署后重新检查公网 403、未知用户拒绝、管理员接口拒绝及服务实际环境；旧 health 字段 `realMoneyAllowed=false` 不能证明微信不会扣真实资金。当前优先完成关闭新购、保留对账的修复，未核验前不恢复购买。
4. 在 Android/Windows 微信客户端真机调试执行下面的支付、断线恢复、退款用例。每次可能拉起支付前，先向用户明确套餐金额及沙箱可能实际扣款，获得该笔金额确认；最终以微信收银台为准。扫码、支付确认或设备解锁由用户亲自完成，不需要发送验证码、密钥、OpenID 或 token。未获得金额确认不得再次调用支付。
5. 记录证据：版本、测试时间、脱敏订单编号、官方订单终态、各表行数变化和权益变化；失败保留原订单并查单，不能换单重付来掩盖未知结果。测试结束恢复 closed，保留订单及审计，不删测试账本。

## 验收矩阵

| 用例 | 动作 | 必须看到的结果 |
| --- | --- | --- |
| 正常支付 | 一名测试者购买一份 photo10 | `signData.env=1`；渠道查询 `env_type=2`，支付状态 2/3/4、商品/金额/用户/单号匹配；本地一单、一份 10 次权益；发货终态最终可查。 |
| 金额确认取消 | 显示具体金额和可能实际扣款提醒后取消，或弹窗失败 | 不调用 `client.buy` 或 `requestVirtualPayment`，不清除已有 pending；确认期锁定按钮，避免双击。 |
| 连点与并发 | 连点购买、同一幂等键并发提交 | 只产生一个业务订单；同键不同商品/参数拒绝；任何客户端 `success` 都不能直接授予权益。 |
| 用户取消 | 拉起后取消，刷新和重新打开 | 以渠道查单为准；未付款不增加权益。取消回调不能被误当“明确未支付”并直接重发新单。 |
| 付款后退出 | 支付后关闭小程序、缺失前端成功回调，再打开 | 后端补查/推送仍可结算；用户同一账号恢复原订单与权益，不依赖客户端存储为账本。 |
| 通知重复/乱序 | 同一沙箱通知重复、先轮询后通知、重启后再通知 | 授权次数只增加一次；发货任务只完成一次，不回退订单终态。伪造金额、环境、用户、商品拒绝。 |
| 渠道超时 | 在隔离测试中模拟查询超时/不明确响应；远端只做可控故障演练 | 本地保持待确认；无新权益、无自动再次支付；恢复后按原单完成。不能在生产网络制造故障。 |
| 权限隔离 | 两名独立测试微信账号互查订单、退款、权益 | 非本人订单返回拒绝/不存在；共享设备换号不会显示或提交上一账号订单。需第二账号实际配合，模拟对象不能替代实测。 |
| 未消费退款 | 本人申请，限定审核通过，后台发送一次退款 | 退款申请/审核/启动均不是终态；官方退款单类型 1、状态 8、env_type=2、金额/单号及凭证匹配后，本地退款 succeeded，权益撤回一次。状态 5 仅商户侧扣款完成，继续等待用户收款。此项已于 2026-10-09 纠正并补回归测试。 |
| 退款结果丢失 | 退款提交超时或回调丢失 | 使用原退款单号查询；不生成第二笔退款，不因超时恢复已退款权益。 |
| 重复退款通知 | 已确认退款后重放相同通知及重复补查 | 不重复减少余额，不恢复已撤回权益，审计能定位原操作。 |
| 使用与退款竞争 | 隔离测试并发预占、完成、退款 | 同一权益不能既消费又退；结果未知保持冻结待核查。真实图片未接通前只计本地账本测试。 |
| 服务重启 | 已有待处理发货/退款任务时受控重启或新版本替换 | durable outbox 从 MySQL 继续；无丢单、重复权益、重复退款。 |

订单查询状态与本地状态不是同一枚举：官方 0 表示尚未成功建单且不可支付；1 已建单；2/3/4 为已支付到已发货；6 已关闭；退款单 5 为商户侧扣款完成，8 才是用户收款完成。2026-10-09 已纠正旧记录将 5/8 均当终态的问题。不能简单把非零状态解释为成功。[查询订单][query]

`notify_provide_goods` 是已交付后的确认补偿，不能用它代替真正交付权益；正常发货推送成功 ACK 后官方不要求重复调用。本项目云入口额外使用该 API 是为了消除“任意调用者假装通知导致误消除 outbox”的歧义。[发货确认 API][deliver]

## 不能从本轮沙箱推出的结果

成功支付及原路退款到账、正式商品审核发布、Android/Windows 正式版、小程序提审、iOS Apple 支付、真实图片成功交付与删除、跨设备实测、备份恢复演练均需独立证据。沙箱可能发生真实扣款，不能将“沙箱/正式”直接等同“无资金/有资金”；本轮原单关闭、权益为零，只证明该单已按查单结果收尾，不证明购买与退款链路验收成功。首轮 Android/Windows 沙箱无需等待 iOS；正式若不支持 iOS 购买，必须真实关闭入口并按届时平台审核要求核对，不能仅在文档里写“暂不支持”。
