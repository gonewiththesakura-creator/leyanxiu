## 已实现行为

| 数据/入口 | 本地实现 |
|---|---|
| OTP 成功、发送失败、第五次错误、退出、账号切换、注销 | 即时置为已消费并清空 `code_hash`。校验入口防御空/损坏摘要，返回 `OTP_INVALID`，避免等长比较抛错。 |
| OTP 五分钟到期 | 批量 apply 扫描清空校验值；验证时也会拒绝并清空到期值。 |
| 24 小时防刷计数 | 使用、退出、注销、到期清码均保留 `phone_hash/ip_hash/device_user_id/created_at`；仅 `created_at < 扫描时刻 - 24小时` 删除整行，保留满窗口。 |
| 会话撤销/注销 | 即时清空 `tokenHash`。批量扫描清空失效会话遗留摘要，并在到期或撤销满七天后删除会话明细。 |
| 设备映射 | 空映射按扫描删除；自然到期满七天后删除。先撤销并持久化设备原临时会话，再删除映射，修复历史设备会话复活窗口。新绑定账号时也撤销该设备原临时会话。 |
| 业务记录 | 不删除账号主键、手机号索引、旧财务设备别名、订单、退款、账本、权益、审计或同意记录；账号条款仍为 `account-v1`，不轮换手机号 HMAC 密钥。 |

没有本次期限方案的 `app_login_challenges` 和 `state.authChallenges` 未纳入本次批量扫描，不能描述为“所有账号数据/挑战均已定期清理”。日志、备份和媒体门禁由其他子任务实施，本报告不作为它们已完成的证据。

## 接口与启动钩子

新增 `server/accounts/retention.js`，不加载 `.env`、不自行读取业务状态、不创建云客户端、不联系短信或模型供应商。

```js
import { createAccountRetention, startAccountRetentionJob } from './accounts/retention.js';

const retention = createAccountRetention({ db, store, flush: flushComplianceStore });
const preview = await retention.run();                  // 默认只读计数
const status = retention.status();

// 先核对预览、完成一致性备份，并在主线程明确启用后才使用 apply。
const job = startAccountRetentionJob(retention, {
  apply: false,                                        // 默认持续只读扫描
  onResult: report => reportCounts(report),
  onError: event => reportFailure(event),
});
await job.ready;                                       // 启动即扫描
// 每 300000 ms 再扫，无须收到 HTTP 请求；正式启用批量操作用 apply:true。
await job.stop();                                      // 停后续调度，并等待在途扫描
```

上例 `reportCounts/reportFailure` 由主线程接入已有监控，禁止记录行内容、手机号、验证码、令牌或密钥。生产钩子与健康门禁的集成由主线程完成；示例本身不是部署指令。

`run({apply:true})` 返回实际计数；dry-run 返回候选计数。字段包括 `otpRowsDeleted`、`otpValuesCleared`、`deviceMappingsDeleted`、`sessionsDeleted`、`sessionTokenHashesCleared`、`invalidSessionTimes`，不输出记录 ID。预览与 apply 之间可能有新请求，不能把预览当作锁定的删除清单。

状态含 `running`、`lastRunAt`、`lastSuccessAt`、`lastAppliedAt`、`lastError`、`lastReport`；超过两次扫描周期没有成功扫描时 `overdue=true`。任务额外报告 `stopped` 和 `lastNotificationError`。扫描失败、停机、超期或异常时间字段应进入监控；dry-run 的成功不等于实际清理已启用。

## 事务及失败边界

1. 超过 24 小时的 OTP 行删除使用已有 `system:sms-limit` 锁，与发送预算一致。
2. 批量清验证码及设备映射清理使用 `system:account-binding` 锁，与验证/账号切换一致，避免持不同锁批量更新同一设备 OTP 产生互等。两步不嵌套不同连接事务。
3. 会话通过 `store.retainAccountSessions` 和现有 SQLite 快照事务修改，不绕过存储接口修改数据库。
4. PostgreSQL 和身份存储不具备跨库原子提交。失败可能已有部分安全清理完成；状态返回失败，不报告全量完成，下一次幂等重试。历史设备会话先持久撤销再删 PostgreSQL 标记，持久化失败则标记保留供重试。
5. 调度通知自身失败也捕获并报告状态，避免后台 Promise 未处理拒绝。shutdown 应等待 `job.stop()` 后再关闭数据库。

覆盖只读扫描不写数据、五分钟及 24 小时/七天精确边界、手机/IP/设备/全局预算不被重置、即时清凭据、历史临时会话不复活、新设备证明仍可登录、财务和最新撤回状态不变、无 HTTP 请求的定时扫描、并发扫描拒绝、持久化与通知失败重试、SQLite 重启持久性。临时文件在持久化 flush 及子进程退出后清理。

第一次使用系统 Node `v24.14.0` 发现已装 `better-sqlite3` 原生 ABI 对应 Node22，另出现临时 JSON rename 的 `EPERM`；切换项目现有 Node22、修正测试账库夹具并补显式 flush 收尾后，专项和必要回归全部通过，未修改依赖 ABI。

PGlite 可以验证真实 SQL、约束和事务回滚，但这里的事务包装不能替代真实 PostgreSQL 多连接行锁并发验收。线上首次只读计数、一致性备份、显式启用 apply、断网/停机监控和真实 PostgreSQL 多连接验收仍由主线程在后续受控集成中完成。
